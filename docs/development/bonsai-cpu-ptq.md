# PTQ1_0 CPU kernel provenance and validation

This AVX2 slice targets Bonsai 2 ternary weights in the existing `PTQ1_0` format. It keeps the 28-byte, 128-weight block and the four independent Q8_0 activation scales. SSE2, SSSE3 and scalar fallback implementations remain available.

The AVX2 layout and arithmetic are adapted from [lenny76's Prism pull request #250](https://github.com/PrismML-Eng/llama.cpp/pull/250), rebased upstream commit `300913b5273f4d96cddb892930d4814ad1bce6f4` on branch `rebase/250-on-prism`. Author: lenny76. The original commit credits Claude Opus 5.5 as co-author. This narrower adaptation keeps the function in place and imports only the AVX2 path; its AVX-512 path is outside this slice. The upstream MIT license and notices remain in this repository.

Each 32-byte output vector matches one Q8_0 sub-block. PTQ1_0 stores five runs from its first 16 bytes, five runs from its next eight bytes, and four two-byte runs from `qh`. Byte multiplication modulo 256 and in-lane shuffles join these runs in element order. Two unsigned thresholds recover codes 0, 1 and 2. The integer dot subtracts the activation sum to obtain signed ternary values, including when an activation is -128. VNNI uses the existing `GGML_DPBUSD_256` feature gate; other AVX2 builds use `maddubs` and `madd`. Products remain far inside the signed 16-bit saturation bound in that fallback.

Float partial sums stay in eight lanes until one final horizontal reduction. FMA and the changed summation order can change the final bits and generated text. Weight storage and activation quantization do not change. Numerical tests alone do not establish end-to-end quality or throughput.

The existing `test-quantize-fns` now checks all packed-byte patterns with mixed dyadic scales at 128, 384, 2048, 5120, 6144, 10240 and 17408 values. Separate one-hot tests check every trit position with -128 and +127 activations. Mixed non-dyadic FP16 scales compare against a double-precision dot of independently dequantized values, with a cancellation-aware bound based on the sum of absolute products.

Full Bonsai 2 projection matrices live in `test-backend-ops`' performance collection and are not selected by correctness mode. Its correctness collection already tests 5120, 6144 and 17408 row widths with smaller output matrices. This slice adds explicit correctness cases at row widths 128, 5120, 6144, 10240 and 17408, output row count 31, and token counts 1, 2, 3, 4 and 8. Each runs with both F32 activations converted to Q8_0 and direct Q8_0 activations. Additional cases use padded rows, output row count 7, and broadcast planes at widths 128 and 5120. These bounded matrices verify model row widths, conversion and indexing; they do not verify full projection output sizes or model behavior. Select the correctness collection with `test-backend-ops test -o MUL_MAT -b CPU -p ptq1_0`.

## Development-host validation, October 6, 2026

Windows, Intel Core Ultra 9 290HX Plus, MSVC 19.44, Release. The AVX2 non-VNNI build passes `test-quantize-fns` and the original 174 PTQ backend correctness cases. The AVX-VNNI build passes `test-quantize-fns` and all 236 cases, including the added bounded matrices. The SSE2 fallback build passes `test-quantize-fns`. AVX-VNNI support was verified with CPUID before executing that build. These are native Intel host checks, not AMD or EliteBook validation.

Initial serial `tg32`, three-repetition measurements at 16 threads changed from 3.907 to 5.244 tokens/s against the same source/compiler/AVX2 flags. These short, synthetic decode calls are diagnostic evidence only. Rig's measurement scripts retain raw timings, runtime-library hashes and process memory; reversed-order repetitions, direct HTTP latency and long-context/agentic acceptance remain separate work. See the Rig repository's `docs/bonsai-cpu-results.md` and `docs/bonsai-cpu-plan.md` for the current evidence and CPU exhaustion ledger.

Model KLD/perplexity, representative coding/tool behavior, sustained long-horizon latency, target Intel/AMD hardware and non-x86 execution remain unverified. This fork is experimental; Rig's shipping engine pin is unchanged.

## Compact GEMM slice

This is preserved experimental research and is disabled by default. The direct `PTQ1_0`/`Q8_0` case in `llamafile/sgemm.cpp` handles two or more token columns when explicitly enabled. Single-token calls keep the vec_dot path. It follows the existing `tinyBLAS_PQ2_AVX` tile scheduling and tail partitioning, currently using two output rows and two token columns, with one-row and one-token tails. Its PTQ codec is shared with the first slice in the private C/C++ header `arch/x86/ptq1_0.h`; the byte mapping and unsigned dot retain lenny76's attribution above.

Compact weights are decoded per output row and reused across the tile's token columns. Each activation sum is reused across output rows. The four Q8_0 scales stay independent. Float FMA operations follow the vec_dot block/sub-block order and use the same final reduction. There is no model transcode, loader change, persistent activation staging or full weight expansion. The existing caller preserves padded weight strides, converted activation rows and broadcast planes. Non-contiguous direct Q8_0 activations keep the existing fallback.

The new dispatch returns false when `params->use_ref` is set, so backend correctness compares GEMM against the validated vec_dot path rather than against itself. CPU PTQ matrix cases require zero NMSE. Existing independent packed-byte, one-hot and double-reference dot tests still check the shared codec. Additional correctness cases cover all one/two-row tile shapes, token tails through nine columns, real model row widths, padded weight rows, broadcast planes and permuted input strides. Full projection matrices remain in the performance collection.

Set `GGML_PTQ1_0_GEMM=1` before starting a process to enable this experiment. An unset variable, `0`, or any other value keeps the existing path. The environment flag is read once with thread-safe C++ static initialization. Non-AVX2 builds retain the existing paths. This GEMM has not met its performance acceptance criteria and is not a faster replacement for the established vec_dot path.

The flag's semantics changed only after the attempt 4 measurements. Those binaries enabled GEMM when the variable was unset or had any value except exactly `0`; the current source enables it only for exactly `1`. Earlier reports retain their original settings, source/runtime hashes and metrics. Inherited `BaseVersion`/`build_commit` `8f2581aa5` alone does not identify the uncommitted experiment; use its recorded source and DLL hashes. The release/integration pin remains `8f2581aa5`, without this experimental GEMM. Final unset/`0`/`1` toggle validation remains required after rebuilding the opt-in change.

### Revision guided by MSVC code generation

The first attempt staged all eight decoded vectors for a two-row tile. In the MSVC 19.44 `gemm<2,4>` object, three of eight accumulators were read and written on the stack inside every 32-weight sub-block update; the other five were saved and reloaded around each full-block unpack. The `gemm<2,2>` dot loop kept its four accumulators in registers but saved them around the unpack phase. The shared vec_dot unpack was fully inlined without a hot-loop code array or accumulator spill. The first attempt's source and hashes are preserved in the Rig repository under `artifacts/bonsai-cpu/20261006/gemm-attempt1-source/`.

The revision updates one 32-weight group at a time using four compile-time group indices. Its C/C++ selector uses the existing 128-weight mapper, so it introduces no second trit layout. Constant propagation can discard the three unused results before code generation. Each update has at most two decoded vectors logically live; compiler inlining and register allocation still need verification in the rebuilt object. Group order, scales, reduction and the single-token vec_dot source remain unchanged. FP16 conversion continues to use the same CPU macro as vec_dot. Rebuild validation must inspect emitted code before throughput comparisons, then repeat zero-NMSE backend tests and reversed-order model measurements with single-token negative controls.

The second attempt passed quantization and all 291 backend cases with zero NMSE, but failed the register-retention review. MSVC removed unused group results and helper calls, yet kept all eight accumulators on the stack in `gemm<2,4>` and all four in `gemm<2,2>`. Its two-by-four frame grew from `0x348` to `0x408`, with about 2 KiB of accumulator traffic per 128 weights. Source, hashes and disassembly summaries are preserved in the Rig repository under `artifacts/bonsai-cpu/20261006/gemm-attempt2-source/`; this attempt was rejected before throughput validation.

The third attempt used explicit `acc00`, `acc01`, `acc10` and `acc11` vectors in a two-by-two tile. A small forced-inline helper accepted and returned one accumulator by value. Four explicit constant-group blocks removed array-reference escape. It passed quantization and all 291 zero-NMSE backend cases, but MSVC left two full-block unpack calls inside the K loop and staged many vectors on the stack. Its frame was `0x4E0`. Source, hashes and disassembly summaries are preserved under the Rig repository's `artifacts/bonsai-cpu/20261006/gemm-attempt3-source/`; throughput validation was rejected.

The fourth attempt gives the 32-value group decoder a direct, forced-inline path instead of selecting an element from a full-block temporary array. Its four explicit cases use bounded 16-byte loads at block offset 0 or 12 (both inside the 28-byte block). Shared read-only coefficient and shuffle tables serve both the 128-value and 32-value decoders; their values exactly match the prior vector constants. The two-by-two kernel uses four named accumulators and a compact group loop in ascending order to keep only two decoded vectors live. Tail pointer guards, vec_dot arithmetic, scales and final reduction stay intact. Changing constant construction can still change compiler scheduling, so rebuilt code inspection and single-token regression remain required before any performance claim.

Attempt 4 passed quantization and all 291 zero-NMSE backend cases under both MSVC 19.44/OpenMP and clang-cl 19.1.5 with the native threadpool. Both compilers eliminated unpack helper calls, but still spilled all four accumulators around group updates. MSVC's two-by-two frame was `0x1C0` (345 instructions); Clang's was `0x1B8` (375 instructions). Register-retention acceptance was not met.

Condition-aware reversed `pp64` comparisons rejected the candidate: MSVC GEMM enabled was approximately 8.58 tokens/s versus 9.09 disabled (about 5.6% slower). Clang/native-threadpool GEMM enabled was 7.875 tokens/s versus 9.068 disabled (about 13.2% slower). These are within-binary comparisons on the development host; the compiler/threadpool arms are separate experiments. Earlier short apparent improvements and varying single-token negative controls do not establish a speedup. Rig's raw reports retain the original timings and conditions. Attempt 4's source, hashes, prior flag semantics and disassembly summaries are preserved under `artifacts/bonsai-cpu/20261006/gemm-attempt4-source/` in the Rig repository.

All four attempts remain available for review, but none establishes a validated faster GEMM. Another kernel revision should follow operator-level attribution of PTQ matmul, Hadamard rotation, activation quantization, recurrent GDN, attention and synchronization costs. No profiler framework or shipping runtime dependency is introduced by preserving this research.
